## 竞品 AndroMeld 的 Mac 候选窗定位机制（分析，未改代码）

用户反馈：竞品的 Mac 输入法候选窗贴在手机光标下方，我们的飘在别处。定位到根因并给出改法。

**根因**：macOS 候选窗位置只认宿主给它的 caret 矩形。
- 竞品（原生 AppKit）自己实现 `NSTextInputClient`，`firstRectForCharacterRange:actualRange:` 返回手机光标换算到 Mac 屏幕的矩形 → 候选窗贴着手机光标。
- 我们（Electron/Chromium）无法重写该方法；Chromium 用**聚焦元素的 DOM caret 矩形**充当它。`.mirror-mactext` 是 1×1 隐藏 input，靠 grid 叠在 `.mirror-screen` 里、**没有任何 left/top**，所以它的 caret 落在画面区左上角 → 候选窗跟着跑偏。

**改法（推荐 A，Electron 可行）**：把隐藏 input 改成绝对定位，锚到"手机光标 → 窗口 CSS 坐标"的映射点上，光标移动时更新 left/top。
- 光标来源三选一：① 最近一次 pointerdown 的视频坐标（`useMirrorInput.js` 的 `videoCoords()` 现成）；② `uiautomator dump` 拿聚焦 EditText 的 bounds（adb，零权限，焦点变化时刷）；③ 设备侧 IME 的 `onUpdateSelection`（只给字符偏移，坐标仍需 ②）。
- 坐标反算 = `videoCoords()` 的逆变换。
- 光标推进：每次 commit 后按已提交文本宽度前进（canvas `measureText`，CJK 退化为 fontSize/字）。
- 注意：移动只能用 left/top，重挂 DOM 会 blur；必要时 `setSelectionRange` 触发 Chromium 重算 caret bounds。
- 改法 B（原生，竞品同款）= 在 Electron 窗口上挂一个实现 `NSTextInputClient` 的 NSView 抢 first responder，工程量高。

**重要澄清**：`NATIVE_MIRROR.md` §G1 里"读不到第三方输入法候选词表"那条结论**不影响定位**——候选窗本来就是 macOS 画的，词表来自 Mac 输入法，我们只需要把锚点给对。

**最小验证（尚未做）**：把 `.mirror-mactext` 改 `position:absolute`，点击画面时移到点击点，看候选窗是否跟着走。

## 候选窗锚点 Slice 4b 真机第一轮（2026-10-11 下午晚些）

用户口述：**候选窗位置确实变了，但不特别精确** ⇒ 机制成立（Electron 里 Chromium 拿 DOM caret 矩形当 `firstRectForCharacterRange`），剩的是精度。

**加了 dev 探针**：`devTools && macTextAnchorCss && macTextCapturing()` 时在锚点画红圈（`.mirror-mactext-probe`）。判据二选一 —— 红圈压不住手机真实光标 ⇒ 取点问题；压得住而候选窗仍偏 ⇒ macOS 摆放问题。

**偏差的两个来源**：
1. **取点不准**：tap 点 ≠ 手机 caret（插入点吸附到字符边界；聚焦后我们的输入法视图弹出、前台 app 可能 `adjustResize` 把内容顶上去，锚点按点击那一刻算就再也不动了）。
2. **macOS 摆放**：候选窗摆在宿主给的 caret 矩形**下方**，而我们给的是 1px 高矩形（`font-size: 1px`），手机光标却是一条 ≈ 一个行高（16sp × density/160，1080p ≈ 42px）的竖线 ⇒ 要把字段做成一个行高的矩形、底边对齐光标线底。**这条不用设备侧配合。**

**精确解（已上网核实）**：`CursorAnchorInfo`（API 21+，`InputMethodService.onUpdateCursorAnchorInfo`）**明确是屏幕坐标**下的插入点，官方定位就是"让 IME 在真实插入点附近画 UI"，`getInsertionMarkerHorizontal/Top/Bottom` 正是缺的那份坐标。⚠️ 但**由前台 app 主动调 `updateCursorAnchorInfo()` 才下发**，不是所有应用都报（读不到是 `NaN`）⇒ 必须做成**机会式**：设备报得到就用，报不到退回 tap 点。走既有桥加 `{op:'caret',x,y,h}`；同一条通道顺带解决"连续打字锚点不跟随"。

## 候选窗锚点 Slice 4c —— 抄竞品的 `CursorAnchorInfo`（2026-10-11 晚，代码+APK 就位，缺装包验证）

用户追问：「andromeld 怎么做的？能不能抄」。**能抄**。上面第二轮那条"`CursorAnchorInfo` 作废"的结论**是错的**，本轮推翻。

**竞品怎么做的（实证）**：
- Mac 端是原生 AppKit（无 Electron Framework），自带 `adb` + `andromeld-mcp-server`，含 `WebRTC.framework`；二进制里有 `caretRect` / `caretWidth` / `currentCaretX` / `currentCaretHeight` / `currentCaretOriginY` / `leadingText` / `currentSelectionLocation` 一组字段 —— 这些**是设备端报上来的真实光标矩形，不是自己攒的**。
- 设备端 APK 有 `MirrorInputMethodService` / `MirrorImeServerBridge` / `MirrorImeBridgeBinderParcel` / `Shizuku`，以及 **`requestCursorUpdates` 与 `getInsertionMarkerHorizontal/Top/Bottom`**。
- ⇒ 竞品公式 = **设备侧上报光标屏幕矩形 + Mac 端把它当 caret 矩形交给系统**。我们 4b 已解决后半段（Electron 用 DOM caret 矩形充当 `firstRectForCharacterRange`），4c 补前半段。

**认知修正（重要）**：`dumpsys` 里 `mCursorRect=0,0-0,0` 不是"Android 拿不到光标像素位置"，而是**没人向编辑器订阅**。`InputConnection.requestCursorUpdates(int)`（API 21+，`CURSOR_UPDATE_IMMEDIATE=1` / `CURSOR_UPDATE_MONITOR=2`）主动订阅后，编辑器才把 `CursorAnchorInfo` 推进 `InputMethodService.onUpdateCursorAnchorInfo()`。已核对 android-36 SDK，两处 API 都在。**教训：静态观测"没看到值"≠"拿不到值"，尤其在它有"需先订阅"语义时。**

**落地（四处，各归各位）**：
- 设备侧 `MirrorInputMethodService`：`onStartInput`/`onStartInputView` 调 `requestCaretUpdates()`（`CURSOR_UPDATE_MONITOR`，`try/catch (Throwable)` 包住）；`onUpdateCursorAnchorInfo` 读三个 `getInsertionMarker*`，`NaN` 跳过，否则 `bridge.notifyCaret(true,x,top,bottom)`；`onFinishInput` 报 `notifyCaret(false,…)`。**纯上报，不改输入行为**。`MirrorBridge` 加 `notifyCaret` → `{"op":"caret","valid":…,x,top,bottom}`。
- 桥 `macBridge.js`：`handleLine` 认 `op === "caret"` → `readCaret(msg)` → `onCaret?.(rect)`；`readCaret` 对 `valid===false` 或字段非有限数回 `null`。`direct-session.js` 透传 + 导出订阅口 `onMacKeyboardCaret(listener)`。
- 渲染层 `App.vue`：新增 `macTextDeviceCaret`；`macTextAnchor` **优先采用设备报的真实光标**（`caretRectToAnchor`），拿不到才退回 4b 自攒；`macTextCaretHeightPx()` 同理。`macTextAnchor.js` 加纯函数 `caretRectToAnchor`，测试补到 11 条。
- **helper 版本抬到 `versionCode 11` / `versionName "1.10"`**（原 10/1.9）。⚠️ 必须抬：桌面端靠「随包 `helper-app.version.json` 的 versionName ≠ 设备已装版本」触发自动安装（`electron/adb.js` ~L1277），不抬则 4c 的设备侧代码永远上不了手机。versionName 的规律是 `1.(versionCode-1)`。

**未知项（装包后先验这两条）**：
1. `requestCursorUpdates` 对 MIUI 笔记的 `RichEditorWebView` 是否有效（WebView 的 `InputConnection` 实现差异大，`EmojiInputConnection` 还包了一层）。
2. `getInsertionMarker*` 是否**屏幕坐标**（代码按屏幕坐标实现）。若发现系统性偏移（如总差一个状态栏高度），大概率是这里。

**校验**：oxlint 0 错 / eslint 0 错 / tsc 0 错 / vitest 42 文件 510 通过 / `vite build` 绿；helper `assembleDebug` 成功，APK 内已确认含 `requestCursorUpdates` / `onUpdateCursorAnchorInfo` / `getInsertionMarker*` / `notifyCaret`。顺手修了两处注释问题：`macBridge.js` JSDoc 第 27 行缺 `*` 前缀、`macTextAnchor.js` 里 `estimateAdvancePx` 还留着被推翻的旧结论。文档已同步 `NATIVE_MIRROR.md` §G1（纠正"作废"结论 + 补 Slice 4c）与 `TODO.md` §6.2 G1 行。

## Slice 4c 真机验证（2026-10-11 晚）—— 链路通，但坐标系不对，默认关闭

**怎么验的（不依赖 Electron 应用）**：`adb forward tcp:9999 localabstract:anddrive-mac-keyboard` + 自写 Node 旁听器（`/tmp/caret-probe.js`、`/tmp/caret-commit.js`），用 `settings get global anddrive_mac_keyboard_token` 的值做握手。设备侧另插临时 `Log.i("AndDriveImeProbe", …)` 看三层走到哪一步。

## Slice 4c 反转：漏了 `getMatrix()` —— 补上后坐标正确，已启用（2026-10-11 晚）

上一节那个"坐标系不对、默认关闭"的结论**是错的**，我自己踩了坑又爬出来。**真正的缺失是一步 `getMatrix()`。**

**官方契约（逐字，`CursorAnchorInfo`）**：
- `getInsertionMarkerHorizontal/Top/Bottom/Baseline`、`getCharacterBounds` —— 全部**"在本地坐标中返回……将在屏幕上呈现时使用 `getMatrix()` 进行转换"**。
- `Builder.setInsertionMarker` —— "as a rectangle in **local coordinates**"。
- `getMatrix()` —— "返回 `Matrix` 的新实例，该实例指示要在此类中应用其他位置数据的变换矩阵。"
- ⚠️ 而**类摘要**写的是"此类将文本插入点和组合字符串的位置封装在**屏幕坐标**中" —— 那句说的是**过矩阵之后**的结果。**只看摘要就会以为拿到的已经是屏幕坐标。** 这次就是被它带偏，白跑一轮。

**修法**（设备侧，`MirrorInputMethodService.onUpdateCursorAnchorInfo`）：
```java
float[] points = new float[] { x, top, x, bottom };
Matrix matrix = info.getMatrix();
if (matrix != null) matrix.mapPoints(points);
bridge.notifyCaret(true, points[0], points[1], points[3]);
```
变换在**设备侧**做，协议不变（桥报的仍是 `x/top/bottom`，只是现在确定是屏幕 px）。

**真机复验（Mi 10 / MIUI，raw 与 matrix 一起打出来对照）**：

| 应用 / 控件 | 控件屏幕边界 | raw（本地） | matrix | 变换后（屏幕） |
| --- | --- | --- | --- | --- |
| MIUI 短信 · 收件人框 | `[526,467][609,579]`（高 112） | `0 / 30 / 82` | 纯平移 `(526,467)` | `526 / 497 / 549` |
| MIUI 笔记 · 正文（WebView） | `[66,491][1017,2206]` | `195.6 / 335.3 / 356.4` | 缩放 `2.75` + Y 平移 `244` | `538 / 1166 / 1224` |

**两处独立佐证（不是"看着像"）**：① 收件人框的矩阵平移量 `(526,467)` 恰好等于该控件屏幕原点；变换后行顶 `497 = 467+30`，而该框高 112、行高 52、垂直居中 ⇒ 行顶偏移应为 `(112−52)/2 = 30`，两条路同一个数。② WebView 的矩阵是缩放 `2.75`（设备像素比）+ Y 平移 `244`，而 uiautomator 报的 WebView 边界正是 `[0,244][1080,2206]`；`195.6×2.75=538`、`335.3×2.75+244=1166`，1166 落在正文框内。**WebView 那条同时印证了 raw 是 CSS px**（高度 21.1 ≈ 16px 字号 × 1.3）。

## 修掉「输入中会多个空格」的真 bug（2026-10-11 14:12）

用户：「**输入中感觉会多个空格**」。

**根因（三步闭环）**：
1. 中文输入法用**空格选候选**时，macOS 吃掉空格并提交候选词 → 走桥 `commitText(word)`。
2. **同一个空格还照旧冒到 `window` 的 `keydown` 上**。`shared/keys.js` 里 `' ': KEY_CODES.space`，空格**在** `KEYBOARD_KEYS` 表里；而 `useMirrorInput.js` 的 `onKeyDown` 在 `keyCode !== undefined` 时**提前 `return`**，那句"Mac 键盘在收字就别再发一遍"的 `captureText()` 闸在**后面的可打印字符分支**里 ⇒ 空格永远轮不到那道闸。
3. 设备端我们的输入法**不拦按键**（`MirrorInputMethodService` 没实现 `onKeyDown`），所以那条 `KEYCODE_SPACE` 被编辑器当成**真的空格**插了进去。⇒ 手机上多一个空格。

**回车选候选同理**（会多一个换行），只是用户没报。

**改法**：按键归属抽成纯函数 `src/mirror/keyRouting.js`（`routeKeyDown()` / `isImeKey()`），把**"输入法正在消化这个键"（`event.isComposing || keyCode === 229`）排到查 `KEYBOARD_KEYS` 之前**，命中的键一个都不转发（候选词本身走 `compositionend` 那条文本路）。`useMirrorInput.js` 改成按 `routeKeyDown` 的返回值分派；顺手加 `forwardedKeys` 集合 —— `keyup` 只补发真的发过 `down` 的键，免得被吞掉的键再冒出一个无主的 up。判据 `tests/mirror/keyRouting.test.js`（14 条）。

**教训（写进文档了）**：同一个"谁负责这个键"的问题上**两条判据叠着**（输入法有没有吃掉 / 可打印字符归谁），写成一行行 `if` 时极易把一条漏在提前 `return` 后面。**判据叠两层就抽成纯函数并补单测，别靠读代码确认。**

**校验**：oxlint / eslint / tsc 0 错；vitest **43 文件 524 通过**（+14）；`vite build` 绿。文档已同步 `NATIVE_MIRROR.md` §G1 Slice 4 与 `TODO.md` §6.2 G1 行。

⚠️ **自己踩的坑**：改文档时用 Edit 替换，`old_string` 只写了后一条、`new_string` 忘了把**前一条原样带上**，把「关不掉 / adopt()」那条整段删掉了。已从上一轮的 grep 输出恢复。**教训：在长文档里"插入一条"时，`old_string` 要锚在插入点之后的稳定文本上、且 `new_string` 必须包含它；替换完立刻回读一遍确认前后条目都在。**

**改法**：
- `src/mirror/macTextCapsule.js`：新增 `CAPSULE_WIDTH_RATIO = 3.4`；`capsuleRect(css, screenWidth)` 多返回 `width`（只由高度决定 ⇒ 与合成串无关），并把 `left` 夹进 `0 … screenWidth − width`（画面宽缺省/0/非有限数**不夹**）；`capsuleBox()` 同签名。
- ⚠️ **夹的是同一个矩形**：`macTextAnchorStyle`（交给 macOS 的 caret 矩形 = 字段位置）与胶囊样式都出自 `capsuleRect()` ⇒ **字段与胶囊一起夹**，"两层同源"这条不变量守住。只夹胶囊会让两层在同一屏里错开 —— 那是前几轮一直在修的现象。代价：靠右缘打字时矩形整体左移、候选窗跟着左移，与手机光标错开最多一个胶囊宽。
- `App.vue`：新增 `macTextScreenWidth`，与 `macTextAnchorCss` **同一个出处** —— `syncMacTextAnchor()` 里那次 `getBoundingClientRect()` 只量一次、两个用途（换算坐标 + 夹取宽度），不会"位置是新的、宽度是旧的"。
- CSS：`.mirror-mactext-capsule` 由 `inline-flex` 改 `flex` + `overflow: hidden`（宽度定死，内容不许再撑开）；文字段 `flex: 0 1 auto; min-width: 0; direction: rtl`（装不下时**从头部裁**、保住靠近光标的尾部），光标段 `flex: none`（再长也留在胶囊内）。
