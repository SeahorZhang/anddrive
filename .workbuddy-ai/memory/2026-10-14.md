## 报障：两个镜像声音重叠 / 关掉一个声音回手机（机制已实测确认）

- 用户口径：「打开两个镜像的话声音重叠了，关掉一个镜像，声音又从电脑回到了手机」。
- 排查路径（设备 `af3d7abd`，`dumpsys media.audio_policy` 是唯一有效读数）：
  - 现场就抓到了 bug 态：`Inputs (1)` 里那条 REMOTE_SUBMIX 采集**还是 Active**，但输出侧**没有任何** `Devices: {AUDIO_DEVICE_OUT_REMOTE_SUBMIX}` 的输出（应用音频在 `deep_buffer_out → SPEAKER`）⇒ 手机在放、电脑没声音。
  - 受控实验：写了个只做音频的临时探针（`{video:false, audio:true, control:false, sendDeviceMeta:false}`，用完已删）再起一条采集。结果：**两条采集并存都被接受**（`Inputs (2)`、各 1 个 Active client），并**多出一个 `r_submix output`**（路由被重新应用）⇒ 探针确实收到音频包 ⇒ **两个窗口都拿到同一份混音 = 重叠**。
  - 探针结束（释放其中一条）后：剩下那条仍 `Active`，但 `AUDIO_DEVICE_OUT_REMOTE_SUBMIX` 那个输出**整条消失**、应用输出被挪回 SPEAKER ⇒ **声音回手机**。⇒ 路由是按"最近一次采集的生死"重置的，**不是引用计数**。
- 结论：音频是**设备级**的一条流，不是窗口级。修法必须保证「同一设备同时只有一条采集，且生命周期不短于"该设备还有镜像窗口"」。
- 三个可选方案（已用 AskUserQuestion 问用户）：① 每台设备一条独立音频-only 会话（宿主不随窗口走，两条症状都消，代价是每台设备多一份 jar 推送 + 一个额外 server 进程、第一条窗口的声音晚约 2–3s）；② 只让第一条窗口带音频（~20 行，最小改动，但关掉那条之后剩下的窗口没声音）；③ ①+②折中：第一条窗口带音频，关窗时由剩下的窗口起一条音频-only 会话接管（单窗口场景零额外开销，接管那一下有 ~2–3s 外放空档）。
- 结论写进了 `MEMORY.md` 的「声音在哪出声」一节（含探针的建会话参数），免得以后重走。

## 第五条：双窗口音频的端到端验收（真机跑通了）

用户「你自己来弄」⇒ 我在真机上把第三条那条端到端验收跑完了。**四个场景全过。**

### 怎么把应用跑起来（这套环境有两个坑，下次直接用）

1. **`ELECTRON_RUN_AS_NODE=1` 会被继承进来**（WorkBuddy 自己是 Electron）。不清掉的话
   vite-plugin-electron 拉起的 Electron 会**当 node 跑** `dist-electron/main.js`，报
   `SyntaxError: The requested module 'electron' does not provide an export named 'BrowserWindow'`。
   ⇒ 一律 `env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS <cmd>`。`NODE_OPTIONS` 里那个 shim 也一起清。
2. **`pnpm dev` 的 vite 与它拉起的 Electron 同生共死**（杀掉 Electron，vite 也跟着退）⇒ 想给
   Electron 加参数（`--remote-debugging-port`）不能「杀子留父」，得走**生产包**：
   `env -u ELECTRON_RUN_AS_NODE -u NODE_OPTIONS npx electron . --no-sandbox --remote-debugging-port=9333`
   （`dist/` + `dist-electron/` 都建好了，无 `VITE_DEV_SERVER_URL` 就走 file:// 加载产物）。
   ⚠️ **9222 被 Chrome 占了**，用 **9333**。
3. 驱动方式 = **CDP + 生产 IPC**：`curl 127.0.0.1:9333/json/list` 拿目标 →
   `Runtime.evaluate`（`awaitPromise`）里调 `window.electronAPI.mirror.start({serial,packageName,label,config})`
   / `.list()` / `.stop(id)`；`config` 从 `electronAPI.scrcpyConfig.get()` 拿。
   **镜像窗**里另有 `window.__anddriveIpc`（非隔离窗口 preload 才挂，见 `preload.js` 的 `expose`），
   可以 `invoke('mirror:initGet')` 认出这个窗口是哪个会话、`audioHost` 是真是假；
   还能 `ipc.on('mirror:audioHost', …)` **埋探针记录推送**（这条是"接管信号到没到"的直接证据）。
   **关窗走渲染层 `window.close()`** —— 与用户点红点同一条路（`closed` 派发途中 `stopSession`），
   比 `mirror:stop` 更贴近真实（后者是"窗口还活着"那条路）。窗口标题都一样，只能靠 `initGet` 认人。
4. 注意 `startMirrorSession` 会**复用**同 `serial + packageName` 的既有会话 ⇒ 开第二个窗口必须
   **换一个包名**（这次用 `com.miui.calculator` / `com.miui.notes`）。

## 第六条：浮动态「拖不动窗口」+「三颗超出屏幕」两个报障（真机验收通过）

- 用户口径：「app投屏后不能拖拽了，mac3个彩虹见往右往下点，超出屏幕了」。用 AskUserQuestion 定了两件事：
  ① 「不能拖拽」= **移动窗口**（不是拖边缘改大小）；② 浮动态拖窗区形状 = **顶边整条 24px**
  （从三个候选里选的，他明确接受"手机画面顶部约 24px 收不到触控"这个代价）。
- **根因两条**（CDP + 渲染层量出来的，都是结构问题不是观感问题）：
  1. **浮动态唯一拖窗区是左上角 80×28 的小方块**（`floatDragWidth = mirrorTitlebarNameLeft()`），
     而三颗彩虹键（**AppKit 画在网页内容之上**）正好压在其中间 ⇒ 可抓的只剩几条缝。
     ⚠️ 两个前提缺一不可：`-webkit-app-region: drag` 那一片 **Chromium 一个指针事件都不发**；
     三颗**命中不到**（`DOM.getNodeForLocation` 会命中底下的 DOM 元素，CSS 也盖不住）。
  2. **三颗落在 `(12,7)–(70,21)`**：画面圆角半径 40、圆心 `(bezel + r, bezel + r) = (44, 44)`
     ⇒ 红灯那颗距圆心 48.9 > 40，**一半压在黑色圆角外面**（截图确认「超出屏幕了」）。
- 修法：
  - `MIRROR_TITLEBAR.floatDragWidth` → **`floatDragHeight = 24`**；`.mirror-float-drag` 从 80×28 改成
    **`width: 100%` × `var(--float-drag-height)`**（`--float-drag-width` 这个 CSS 变量一起换掉）。
  - 三颗落点：`MIRROR_TITLEBAR.floatLightX/Y = 24 / 24`（整组最外沿距圆心 25.4、**离弧 ~14.6px 余量**）；
    `mirrorTrafficLightPosition(railFloating)` 改**两档**（窗口态 `{12,7}` / 浮动态 `{24,24}`）。
  - 把画面圆角半径从 CSS 提升成 `options.js` 的 **`MIRROR_SCREEN_RADIUS = 40`（唯一出处）**，
    `App.vue` 的 `--radius` 改从 `windowStyle` 取 ⇒ 几何单测能直接钉"落点在圆内"。
  - `mirror:windowButtons` 载荷 布尔 → **`{shown, railFloating}`**：落点分两档 ⇒ **翻转形态那一拍也得重设**
    （`setWindowButtonVisibility(true)` 会把三颗打回 AppKit 默认左上角，落点每次都与显隐一起设）。
  - `onScreenPointerOut` 的 drag 特判简化成"**两档都是顶边整条**"：
    `clientY ≤ (浮动态 ? floatDragHeight : MIRROR_TITLEBAR.height)`（不再按 `clientX` 分块）。
- **三条实测坑**：
  1. **合成鼠标事件驱动不了原生拖窗**（在拖窗块里按下 + 移动 `120,90` ⇒ 窗口位移 `0,0`）
     ⇒ 验"拖窗区在哪"只能靠 `DOM.getNodeForLocation` 命中测试。
  2. **窗口自己会 resize**（483 → 805 宽，浮动态要重 fit）⇒ 用 `screencapture -R` 截窗前必须**先读
     `screenX/screenY`**，否则截到的是别的窗口。
  3. `screencapture -x -R x,y,w,h` 是**逻辑点坐标**（与 DPR 无关），可直接拿来核对三颗落点。
- 真机验收（设备 `af3d7abd` / Android 17 / SDK 37）：开窗即浮动态（`841×882`）⇒ `.mirror-float-drag`
  `[0,0,841,24]`，沿顶边 `(5,2)(5,12)(100,12)(300,12)(500,12)(700,12)(838,12)` **全命中它**，
  `(300,26)(300,30)(300,60)` 命中 `canvas`；三颗截图确认完全落在手机亮面里、离黑圆角有余量；
  缩到 500 宽回窗口态 ⇒ 三颗回 `(12,7)`、标题在旁边；再放大到 900 又回 `(24,24)`（来回翻转都对）。
